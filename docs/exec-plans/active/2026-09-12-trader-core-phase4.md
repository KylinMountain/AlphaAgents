# Trade Learn Evolve：第四阶段 受控进化

状态：**计划中（尚未开始）**。负责人：本次开发会话。创建：2026-09-12。

> 完成后按 AGENTS.md 的约定移入 `docs/exec-plans/completed/`。
> 本阶段的范围由设计 §14 界定：frozen policy registry、forward shadow accounts、
> fair evaluation、authorized promotion、rollback。完成含义原文是
> **"Evidence controls future policy changes through one audited entry point."**

## 目标

Phase 1 把账算对了，Phase 2 把交易内核补完整了，Phase 3 让学习可归因且**不隐式改变行为**。
于是现在有一条完整的因果链，但它**停在「记录」为止**：

- 我们**能**说出一条知识是被谁、在哪一刻、以什么理由批准的（`knowledge_snapshots`）。
- 我们**不能**说出一条**正在生效**的规则，当初是凭什么证据生效的。

第三阶段的收尾边界已经把这个缺口写死在实现文档 §7：`inject_playbooks`
（`alpha_agents/evolution/feedback.py`）仍按 `playbooks.status` 选行，**不读任何快照**。
所以一条 active 的规则行即使从未进过任何已批准快照，也照样被渲染进提示词 ——
§10 的「未批准不得进入生产决策检索」对候选成立，对 playbook / principle 行**不成立**。
批准因此是**事后可查的存证**，不是**事前生效的开关**。

本阶段的目标：**让证据成为策略变更的唯一闸门，且闸门只有一个可审计的入口。**
具体地说，要让下面这句话从声称变成可检查的事实：

> 任何一条改变行为的规则，其当前生效状态都可以追溯到一次评估、一次批准、一次指针变更；
> 而这次评估用的是**它冻结之后**产生的证据。

## 起点：先量，再设计

本计划的形状不是从设计文档抄来的，是从当前代码与数据量出来的。**这一步的结果决定了本阶段
最该先做什么**，所以放在最前面。

`data/memory.db`（2026-09-12 实测，33 张表）：

| 事实 | 实测值 | 含义 |
|---|---|---|
| `predictions` | 202 行 | 有预测 |
| `predictions.brier` 非空 | **0 行** | **评估货币不存在** |
| `predictions.report_type` | `intraday_signal` 155 / `intraday` 39 / `morning` 8 | **没有任何 `*_shadow`** |
| `gate_decisions` | 3 行（09-08 / 09-09 / 09-11） | 全部 `abstained`、`n=0` |
| `episodes` / `outcomes` / `intents` / `decision_snapshots` / `position_exits` / `learning_candidates` | **各 0 行** | Phase 1–3 的新表**当前为空**（是「截至此刻无数据」，不是「生产从未写入」——两者含义不同，别混） |
| `playbooks` | 1 行（`active`, weight 1.0） | 检索侧的唯一输入 |
| `trading_principles` | 2 行（均 `active`） | 同上 |
| `policy_ref`（`intents` / `decision_snapshots` 两列） | 两表 0 行 | **预留列，恒为空** |
| `knowledge_snapshots` / `knowledge_snapshot_items` | **库中不存在** | 首次调用才建表，即无人用过 |

三条结论，直接决定本阶段的切法：

1. **`holdout_gate.py` 缺的不是调用者，是两半。** D7 记的是「没有调用者」。但即使接上，
   `run_gate` 的 challenger 侧按 `report_type.endswith("_shadow")` 过滤 —— 生产里
   **没有任何写入路径产生 `*_shadow`**；champion 侧读 `get_scored_predictions`，
   而 `brier` 全为空。**两侧都是空的，接上只会得到 `n=0` 的 abstain，和 09-08 那三行一模一样。**
2. **`policy_ref` 是「承诺无可调用入口」的第三例。** 两列已预留、有读侧（`attribution`），
   但**没有注册表可引用**，所以恒为空。本仓库已经抓过两次这个形态，这是第三次。
3. **本阶段最大的风险不是写错，是给不存在的证据造治理。** D7 的教训
   （「一个永远不会触发的闸门比没有闸门更糟，因为它看起来像治理」）会**原样上升一层**：
   一个没有候选、没有证据的晋升服务，比没有晋升服务更糟。因此本计划把
   **「证据路径」排在「治理对象」之前**，并把「现在可检查」与「依赖样本」两类验收分开写。

## 范围

五个切片，按依赖顺序。编号沿用 Phase 2 的 `S`、Phase 3 的 `T`，这里是 `U`。

| 切片 | 状态 |
|---|---|
| U1 冻结的策略注册表 | ⬜ 未开始 |
| U2 影子账户与 challenger 生产者 | ⬜ 未开始 |
| U3 冻结证据上的公平评估 | ⬜ 未开始 |
| U4 授权的晋升与回滚（唯一入口） | ⬜ 未开始 |
| U5 检索闸门：批准从存证变成开关 | ⬜ 未开始 |

### U1 冻结的策略注册表

- 新表 `policy_versions`：一次冻结 = 一个不可变版本，
  `(id, policy_key, parent_id, content_hash, frozen_fields_json, created_by, created_at, note)`。
  不可变性交给 `BEFORE UPDATE` / `BEFORE DELETE` 触发器 `RAISE(ABORT)`（沿用 T2/T4 姿态）。
- 新表 `active_policy`：`policy_key` → `policy_versions.id` 的**单行指针**，带单调递增的
  `version_seq`（U4 的 CAS 靠它）。同一 `policy_key` 只有一行。
- **`content_hash` 必须覆盖真实的行为依赖**：prompt 模板、模型身份与配置、工具契约、
  检索策略、已批准知识快照 id。写入方与校验方投影**同一个字段元组**（Phase 1 / T4 的既成做法），
  枚举顺序不影响哈希。
- **本切片的核心设计决定：注册表登记的必须是「正在运行的策略」，不是一份会漂移的副本。**
  `freeze_policy()` 从**活的配置源**读取并哈希；同一批源可以独立重算出同一个哈希。
  于是「有人改了活配置但没开新版本」不再是一句无人知道的悄悄话，而是**校验失败**。
  这是本切片存在的理由，也是它区别于「再存一份配置」的地方。
- 把 `policy_ref` 写进**新产生**的 `intents` / `decision_snapshots` 行（那两个预留列）。
  没有这一步，注册表就是一个没人引用的装饰品 —— 正是上面第 2 条结论点名的缺陷。

**这一条最容易做错的地方**：把「注册」实现成 `json.dumps(当前配置)`。
那样哈希只能证明「当时 dump 过这个字符串」，不能证明「当时跑的就是它」。
判据见验收 1。

### U2 影子账户与 challenger 生产者

- 这是 D7 的**真正缺口**，也是本阶段能不能验收的分水岭：必须有东西**产生** challenger 预测。
  影子跑以独立的 `trader_id` / run 命名空间 + 一个**冻结到具体 `policy_version_id`** 的
  challenger 策略运行；其预测带可辨识标记，使 `run_gate` 的 challenger 侧非空。
- **隔离是硬约束**（§11）：影子成交不得进入主账户；影子派生的教训不得进入 champion 的
  活跃知识。影子预测/持仓/工作记忆/知识命名空间各自独立。
- **本切片不驱动任何决策**：影子只出预测、只被记录、只被评分，不改变 champion 的任何行为。
- 只读入口：影子覆盖度（跑了几天、有多少条已评分、离 `MIN_VALIDATION_SAMPLES=20` 还差多少）。
  这个入口是本阶段唯一诚实的进度计 —— 它回答「还差多少天」，而不是「做完了没有」。

**风险提示**：这一片在数据上需要**真实的前向时间**才能有内容。代码可以在本轮交付并测试
（用合成但形状合法的输入驱动全路径），但「生产里真的积累了影子样本」只能靠跑。
本计划**不把「已有影子样本」写成验收条件** —— 那会逼着人去编造证据，而 §16 明令禁止。

### U3 冻结证据上的公平评估

- 把 `run_gate` 改成**候选绑定**：`run_gate(policy_version_id)`，
  验证窗口**由该版本冻结的 `created_at` 派生**，不再由调用方传入日期。
- **结构性消除 D7 的根因。** 旧 bug 的形状是 `run_gate("daily_playbook", today, today)` ——
  一个零长度窗口，写得出、跑得动、永远 abstain。所以本切片不是「记得传对日期」，
  而是**让零长度窗口在类型/校验层就构造不出来**：窗口从冻结时间派生，没有默认值能造出空窗。
  没有这一步，D7 会以同样的形状复发。
- `gate_decisions` 增加 `validation_days` **列**。当前它只存在于 `detail_json` 里，
  而 `tech-debt-tracker.md` 的 D7「Recognise」判据写的是「一行 `validation_days` 不为 0」——
  **那条判据现在无法用 SQL 检查**。这是本轮测量顺带发现的口径不一致，一并修掉。
- 评估只从独立事实与冻结协议计算（§12）；**不得**把模型对自己的信心当作 ground truth。
- 「证据不足」是**被记录、可见的**结果（`insufficient`），不是一个静默的 abstain。

### U4 授权的晋升与回滚（唯一入口）

- **晋升 = 对 `active_policy` 指针的一次原子 CAS**，要求同时满足：
  一条**未 abstain** 的 `gate_decisions` 记录 + 一次**人的**批准 + 资格检查
  （冻结哈希未漂移、未决问题已解决）。
- **人的批准复用 T4 的形状**：不可变快照 + 显式 actor / reason / time；
  §11 的「自动评估成功不是晋升许可，且没有任何 LLM 可以批准自己的候选」是硬约束。
- **回滚与晋升同一切片交付，不推迟。** 只有晋升没有回滚是单向门；
  §11 要求回滚恢复一个已批准版本以约束**未来**行为，且**不删除**成交、账本、结果。
- 运维 CLI 是**唯一**写入口（T4 的教训：`approve()` 若无人调用，就是「承诺无可调用入口」）。
  带 `--dry-run`，并**先打印目标数据库路径**（`MEMORY_DB_PATH` 是固定路径、不读 `TMPDIR`）。
- **拒绝路径必须被断言，不是被声称**：rejected / insufficient / 评估失败 / 未批准
  四种情况都**不得**改变指针，也不得改变任何行为依赖哈希。
  用 T4 `TestApprovingActivatesNothing` 的姿态：**全库所有表**逐行 diff，
  断言变化的表**恰好**是允许变的那几张。

### U5 检索闸门：批准从存证变成开关

- 把 `inject_playbooks`（及 principle 的注入侧）从**按 `status` 选行**改为**按已批准快照选行**。
- **这是本阶段唯一改变行为的一片**，也是 §7 明确划给 Phase 4 的工作：
  「要让『未批准即不生效』成立，必须把检索侧改成读快照」。做完这片，
  §10 的不变量才对 playbook / principle 行**成立**，而不只对候选成立。
- 依赖 U1（「哪个版本在生效」由注册表回答）与 U4（指针移动即快照切换），
  因此排在最后。**不采用**「读最近一次已批准快照」这种弱化版本 ——
  那会制造第二个关于「什么在生效」的真相来源，正是 §14 结尾禁止的
  「permanent competing sources of truth」。
- 读侧已经就绪：T4 的 `entity_is_approved` / `candidate_is_approved` / `drifted`
  已经存在且被测试钉住，本切片只需把它接上，不需要新造判断规则。
- **验收方式**：先证明旧实现**泄漏**（一条 active 但从未被批准过的 playbook 会被渲染进提示词），
  再证明新实现不泄漏。先红后绿，不是只测新行为。

## 非目标

- **不做任何形式的自动晋升。** §11：初始批准边界是**人的授权**；
  自动评估成功不是许可，LLM 不得批准自己的候选。本阶段不引入「通过就自动生效」。
- **不编造证据。** 样本不足时，阶段交付的产物是 `insufficient`，不是一个晋升。
  §16 禁止发明缺失的成交、费用、归属 id、批准或策略版本。
- **不迁移生产数据。** 历史 prediction 不补 `brier`、不追溯建 policy 版本、不回填 `policy_ref`。
- **不引入在线强化学习、模型权重更新、自修改生产代码**（§16）。
- **不引入分布式 worker / lease / 消息中间件。** 单写者足够，§16 列为不必要。
- 不改 `predictions.hit` 的现有语义与读者（`review` 的次日校验继续用它）。
- 不新增真实下单、不启动调度、不扩充 lint 豁免基线。
- 不把 U2 的「已积累真实影子样本」写成验收条件（见 U2 风险提示）。

## 验收（机器可检查）

分两类。**第二类不是「以后再说」，而是明确写明「本阶段不可能用生产数据证明」**——
把它写成验收条件就是在要求编造证据。

### A. 本轮代码交付即可检查

1. **注册表登记的是运行的策略**：`freeze_policy()` 的哈希可由同一批活配置源独立重算通过；
   改一处活配置而不新开版本 → 校验**失败**（漂移检测变红）。
2. **指针是 CAS**：两个并发晋升只有一个成功（expected-version 检查）；
   失败方**不改变任何行**。
3. **影子隔离**：影子跑一轮后，champion 可见的每一条读路径输出**逐字节不变**
   （全表 diff，T4 姿态）；影子成交不在主账户。
4. **零长度窗口构造不出来**：`run_gate` 的窗口由冻结时间派生；
   尝试造一个「今天 vs 今天」的调用在类型/校验层失败，且**没有默认值能造出空窗**。
5. **拒绝/不足/失败/未批准不改变任何哈希**：指针 + 全部行为依赖哈希逐字节不变。
6. **回滚不删东西**：回滚后 fills / ledger / outcomes 的行数与内容不变，**只有指针变**。
7. **检索闸门（先红后绿）**：旧实现下，一条 `active` 但从未进过任何已批准快照的 playbook
   **会**被 `inject_playbooks` 渲染（断言旧行为泄漏）；U5 之后**不再**被渲染。
8. **唯一入口**：全仓库只有一个函数能写 `active_policy` 指针（grep 可检查的机器判据）。
9. **D7 的判据可用**：`gate_decisions.validation_days` 是可被 SQL 读的列。
10. 新增回归测试**先证明旧实现失败**，再证明新实现通过；关键不变量用**变异探针**验证测试会红。
11. 全量口径 `.venv/bin/python -m pytest tests/ -q`（**不加 `--ignore`**）、
    `scripts/lint_harness.py`、`scripts/lint_docs.py` 执行并记录实际结果。
12. 不扩充 lint baseline；单个新增模块不超过 1200 行。

### B. 依赖真实前向样本，本阶段只能证明「可达」

13. **晋升路径可达**：一个用**合成但形状合法**的证据驱动的测试，能走完
    冻结 → 影子 → 评估（`validation_days > 0`）→ 批准 → 指针变更的全路径，
    并留下一条非 abstain 的 `gate_decisions` 记录。
14. **生产库在样本不足时产出 `insufficient` 而不是晋升**：对当前生产库
    （`brier` 全空、无影子行）跑一次评估，结果必须是**被记录的** `insufficient`，
    且指针与全部哈希不变。
15. **口径如实**：实现文档 §7 与 README 必须写明「机制已交付 ≠ 已经在跑」——
    即 U1–U5 的机制存在，但**生产里尚未发生一次真实晋升**，原因是样本不是代码。
    这一条本身是可检查的：文档里必须出现这句话，且 `gate_decisions` 里
    **不得**出现任何非 abstain 的生产行来支持相反的说法。

## 风险

- **最大的风险是给不存在的证据造治理。** 上面「起点」三条结论说明：
  评估货币（`brier`）为空、challenger 生产者不存在、注册表恒被引用为空。
  照设计文档字面逐条实现，会得到一个**每一片都有测试、每一片都永不触发**的 Phase 4 ——
  也就是 D7 原样上升一层。**对策**：证据路径（U1 的活配置哈希、U2 的生产者、U3 的窗口派生）
  排在治理对象（U4 的晋升）之前；每张新表必须点名**生产者**与**读者**，
  没有读者的表不建；验收分 A / B 两类，B 类不许伪装成已证明。
- **第二个风险是注册表与现实漂移。** 若注册的是配置副本而非运行中的配置，
  「我们批准的是哪一版」就答不出来 —— 与 T4 拒绝把计数器放进 `version_hash` 是同一个理由。
  **对策**：哈希从同一批活配置源重算；漂移检测是一个变红的断言，不是一个 warning。
- **第三个风险是 U5 悄悄改变行为。** 它是本阶段唯一改行为的一片，
  而它改的正是**模型看到什么**。**对策**：单独成片、单独断言、先证明旧实现泄漏；
  并保留可回退性（快照缺失时必须有明确定义的降级，且降级被记录，不是静默）。
- **第四个风险是单向门。** 只交付晋升不交付回滚，等于把「证据控制变更」做成「一次变更」。
  **对策**：晋升与回滚同一片交付，验收 6 独立钉住「回滚不删东西」。
- **第五个风险是 schema 继续堆进 `memory_store.py`。** 它已 2145 行（D4 第 1 名），
  本阶段还要加 `policy_versions` / `active_policy` / `gate_decisions` 的列。
  **对策**：新表由新模块自持 schema（沿用 T4「不另起 schema 所有权、但由新模块声明」的姿态），
  且**不在本阶段顺带拆** `memory_store.py` —— 拆分是独立工作，混进来会让本阶段的 diff 无法审。
  若新增后仍触到 1200 行上限，先在实现文档记下，按 D4 单独处理。
- **第六个风险是「做了 U5 就等于完成了 §10」。** U5 只让**检索**读快照；
  §10 还包含检索权重、校准器、退役决定等改变行为的路径。
  **对策**：U5 的交付说明必须限定范围 —— 它关闭的是 `inject_playbooks` 这一条，
  不是「未批准即不生效」的全部。
